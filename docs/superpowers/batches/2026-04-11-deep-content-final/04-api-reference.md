# API Reference

This document is the authoritative signature reference for all new surface area introduced by this batch. Consumers — other rime-craft modules, tests, or future batches — should read this before adding new dependencies on the types, components, or store actions.

## Types (`src/types/config.ts`)

### `SpecialInputConfig` (modified)

```ts
export interface SpecialInputConfig {
  enabledTriggers: SpecialTrigger[]    // preset 11 triggers (unchanged shape)
  customTriggers: CustomTrigger[]       // ← NEW, REQUIRED
}
```

**Breaking change**: `customTriggers` is **required**. Any code constructing a `SpecialInputConfig` literal must include `customTriggers: []` at minimum. See [05-migration-guide.md](./05-migration-guide.md) for the rebase checklist.

### `CustomTrigger` (new)

```ts
/** User-defined special trigger that invokes a custom Lua script. */
export interface CustomTrigger {
  id: string              // UUID, generated by store
  name: string            // User-readable name, e.g. "IP 地址查询"
  triggerCode: string     // e.g. "/ip"
  description: string
  scriptId: string        // FK to LuaScript.id
}
```

Constraints:
- `id` is generated via `crypto.randomUUID()` by `addCustomTrigger`. Callers should never set `id` manually (use `Omit<CustomTrigger, 'id'>` in action signatures).
- `scriptId` **should** reference a `LuaScript.id` in the same `SchemaConfig.luaScripts` array, but this is not enforced by the store. The UI shows "⚠ 未关联脚本" for orphaned references.
- `triggerCode` is used verbatim as the right-hand side of a `recognizer/patterns/<fileName>: "^<escaped>$"` YAML entry. The serializer escapes regex-sensitive characters (see `escapeRegExp` below).

### `LuaScript` (new)

```ts
/** A user-authored Lua script registered in the schema. */
export interface LuaScript {
  id: string                            // UUID, generated by store
  fileName: string                      // e.g. "my_translator.lua"
  scriptType: 'translator' | 'filter' | 'processor'
  description: string
  code: string                          // Lua source code
}
```

Constraints:
- `fileName` should match `[a-zA-Z0-9_-]+\.lua`. The `LuaScriptList` UI's filename `<Input>` filter blocks invalid characters during edit, but imported data is not validated.
- The identifier used in YAML (`lua_<type>@<identifier>`) is derived by stripping `.lua`: `fileName.replace(/\.lua$/, '')`. The Lua file's returned function name **must** match the identifier (this is a RIME convention — the serializer does not check).
- `code` is raw Lua source. No parser or linter runs on it — RIME deploys the file as-is and surfaces any errors in `rime.log`.

### `SchemaConfig` (modified)

```ts
export interface SchemaConfig {
  schemaId: string
  fuzzyRules: FuzzyRuleState[]
  switches?: SwitchItem[]
  punctuator?: PunctuatorConfig
  translator?: TranslatorConfig
  spellingScheme?: SpellingScheme
  auxiliaryCode?: AuxiliaryCodeConfig
  reverseLookup?: ReverseLookupConfig
  specialInput?: SpecialInputConfig
  luaExtensions?: LuaExtensionsConfig
  luaScripts?: LuaScript[]              // ← NEW, OPTIONAL
  displayConfig?: DisplayConfig
}
```

`luaScripts` is optional at the type level but the parser always initializes it to `[]` so consumers can read it safely.

## Shared MDX Components (`src/components/shared/`)

Registered in `src/components/shared/mdx-components.tsx`, available as named JSX tags in any `.mdx` file.

### `<Details>`

```tsx
interface DetailsProps {
  title: string
  level?: 'intermediate' | 'advanced'  // default: undefined (no badge)
  defaultOpen?: boolean                 // default: false
  children: ReactNode
}
```

Renders a native `<details>/<summary>` element with a level badge and styled border. The `▶` chevron is a decorative Unicode character that does **not** rotate on expand (cosmetic follow-up noted in [07-known-issues.md](./07-known-issues.md)).

**Level styling**:
- `intermediate` → blue left-border, blue "扩展" badge
- `advanced` → purple left-border, purple "进阶" badge
- (no level) → gray left-border, no badge

**Usage in MDX**:

```mdx
<Details title="原理：lua_translator 的调用链" level="advanced">
  当 RIME 引擎遇到一段编码时... (multi-line content)
</Details>
```

### `<StepGuide>` + `<Step>`

```tsx
interface StepGuideProps {
  children: ReactNode   // must contain <Step> elements
}

interface StepProps {
  title: string
  children: ReactNode
}
```

Auto-numbers child `<Step>` elements (1, 2, 3, ...) in circles with vertical connecting lines. Filters to valid React elements via `Children.toArray(children).filter(isValidElement)`.

**Usage in MDX**:

```mdx
<StepGuide>
  <Step title="创建 Lua 脚本文件">
    在 RIME 用户目录下创建 `lua/my_translator.lua`...
  </Step>
  <Step title="在 schema 中注册">
    编辑 `xxx.custom.yaml`...
  </Step>
  <Step title="重新部署并验证">
    执行「重新部署」...
  </Step>
</StepGuide>
```

### `<YamlPreview>`

```tsx
interface YamlPreviewProps {
  title?: string              // header text above the code
  highlight?: number[]        // line numbers (1-based) — currently only sets data-highlight-lines attribute
  caption?: string            // italic text below the code
  diff?: boolean              // toggles .yaml-preview-diff class for Shiki-based line-diff coloring
  children: ReactNode         // expected to contain a code block
}
```

Renders a `<figure>` with a styled dark `<pre>` container, optional title bar, optional caption, and optional line-highlight/diff data attributes. The actual per-line highlighting is delegated to the downstream syntax highlighter (Shiki, via rehype-pretty-code).

**Usage in MDX**:

```mdx
<YamlPreview
  title="xxx.custom.yaml"
  highlight={[3, 4]}
  caption="第 3-4 行是自定义 trigger 的关键配置"
>
  ```yaml
  patch:
    engine/translators/+:
      - lua_translator@date_translator
      - lua_translator@my_translator
  ```
</YamlPreview>
```

## Store Actions (`src/stores/config-store.ts`)

All 6 new actions operate on `schemaConfigs[schemaId]`. They all:

- Generate UUIDs for new entries via `crypto.randomUUID()`
- Produce new immutable object references (safe for React state)
- Set `isDirty: true`
- Return `{}` (no-op) when the target does not exist

### Custom Trigger Actions

```ts
addCustomTrigger(
  schemaId: string,
  trigger: Omit<CustomTrigger, 'id'>
): void
```

Appends a new `CustomTrigger` to `schemaConfigs[schemaId].specialInput.customTriggers`. If `specialInput` doesn't exist on the target schema, it is created with `enabledTriggers: []` and `customTriggers: [newTrigger]`.

```ts
updateCustomTrigger(
  schemaId: string,
  id: string,
  partial: Partial<Omit<CustomTrigger, 'id'>>
): void
```

Shallow-merges `partial` into the matching trigger. No-op if `specialInput` is absent or no trigger with the given id exists.

```ts
deleteCustomTrigger(schemaId: string, id: string): void
```

Removes the trigger with the given id. No-op if the trigger is not found. Does **not** cascade to remove related Lua scripts.

### Lua Script Actions

```ts
addLuaScript(
  schemaId: string,
  script: Omit<LuaScript, 'id'>
): void
```

Appends a new `LuaScript` to `schemaConfigs[schemaId].luaScripts`. Creates the array if absent.

```ts
updateLuaScript(
  schemaId: string,
  id: string,
  partial: Partial<Omit<LuaScript, 'id'>>
): void
```

Shallow-merges `partial` into the matching script. No-op if `luaScripts` is absent or the script is not found.

```ts
deleteLuaScript(schemaId: string, id: string): void
```

Removes the script. No-op if not found. Does **not** cascade to remove `CustomTrigger` entries that reference this script — those will orphan and show "⚠ 未关联脚本" in the UI until the user rebinds or deletes them.

## Lua Script Templates (`src/data/lua-script-templates.ts`)

```ts
export const LUA_SCRIPT_TEMPLATES: Record<LuaScript['scriptType'], string>

export function renderLuaTemplate(
  scriptType: LuaScript['scriptType'],
  identifier: string,
): string
```

`renderLuaTemplate` substitutes the literal `{name}` placeholder in the selected template with the given `identifier`. Uses `.split('{name}').join(identifier)` to stay compatible with the project's ES2020 TS lib target.

**Template contents** (abbreviated):

```lua
-- translator
local function {name}(input, seg, env)
  if input == "/hello" then
    yield(Candidate("word", seg.start, seg._end, "Hello, World!", "自定义"))
  end
end
return {name}

-- filter
local function {name}(input, env)
  for cand in input:iter() do
    yield(cand)
  end
end
return {name}

-- processor
local function {name}(key, env)
  return 0  -- kNoop
end
return {name}
```

**Caveat**: `renderLuaTemplate` does **not** validate that `identifier` is a legal Lua identifier. Supplying a name starting with a digit or containing a hyphen will produce Lua code that fails to parse at RIME deploy time. See [07-known-issues.md](./07-known-issues.md) item 2.

## YAML I/O (`src/lib/yaml/`)

### `module-yaml.ts` — `MODULE_KEY_MAP`

The `lua-extensions` entry now contains all 6 keys (recognizer + 5 builtin-enhancement sections):

```ts
'lua-extensions': {
  file: 'schema',
  keys: [
    'recognizer',          // (from original special-input)
    'super_comment',
    'super_processor',
    'user_predict',
    'super_replacer',
    'input_statistics',
  ],
}
```

The `special-input` entry has been removed entirely. Any external consumer that iterated `MODULE_KEY_MAP` looking for `special-input` should switch to `lua-extensions`.

### `parser.ts` — `mapToSchemaConfig`

Signature unchanged:

```ts
export function mapToSchemaConfig(
  expanded: Record<string, unknown>,
  schemaId: string,
): Partial<SchemaConfig>
```

**New behavior**:

1. Before building `result.specialInput`, scans `expanded` for two patterns:

   - **Flat patch keys**: `recognizer/patterns/<patternId>: <string>` — iterates `Object.entries(expanded)` and matches the key against `/^recognizer\/patterns\/(.+)$/`.
   - **Nested object**: `recognizer: { patterns: { <patternId>: <string> } }` — reads `expanded.recognizer?.patterns`.

   For each match whose `patternId` is **not** in `SPECIAL_TRIGGER_DEFINITIONS` (the preset list), creates a `CustomTrigger`:

   ```ts
   {
     id: crypto.randomUUID(),
     name: patternId,
     triggerCode: value.replace(/^\^/, '').replace(/\$$/, ''),
     description: '',
     scriptId: '',
   }
   ```

2. Deduplicates by `name` so flat + nested forms don't double-insert.
3. Populates `result.specialInput.customTriggers` with the collected array.
4. Always sets `result.luaScripts = []` so consumers can read the field without undefined-checking. (The parser never extracts Lua source from YAML — Lua lives in separate `.lua` files outside the YAML patch.)

### `serializer.ts` — `serializeSchemaConfig`

Signature unchanged. **New output keys**:

**Custom triggers**: One `recognizer/patterns/<identifier>: "^<escapedTriggerCode>$"` entry per `CustomTrigger`. The `<identifier>` is derived from the linked `LuaScript.fileName` (with `.lua` stripped); if no linked script exists, the trigger's own id is used as a fallback.

**Lua script registrations**: Aggregated into `engine/<type>s/+: <string[]>` entries:

```yaml
engine/translators/+:
  - lua_translator@my_translator
  - lua_translator@another_translator
engine/filters/+:
  - lua_filter@my_filter
engine/processors/+:
  - lua_processor@my_processor
```

Scripts are grouped by `scriptType` and emitted as list-append patches (`/+`). Empty groups are omitted.

### `escapeRegExp` (new private helper)

```ts
function escapeRegExp(str: string): string {
  return str.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')
}
```

Used by the serializer to escape regex-sensitive characters in `CustomTrigger.triggerCode` so `.`, `+`, `?`, etc. appear literally in the emitted `recognizer/patterns/...` regex.

## Test Setup (`vite.config.ts`, `src/test-setup.ts`)

Pre-existing misconfiguration fixed in commit `3776669`:

```ts
// vite.config.ts
import { defineConfig } from 'vitest/config'   // was 'vite'

export default defineConfig({
  // ... existing plugins ...
  test: {
    environment: 'happy-dom',
    setupFiles: ['./src/test-setup.ts'],
    globals: true,
  },
})
```

```ts
// src/test-setup.ts
import { afterEach } from 'vitest'
import { cleanup } from '@testing-library/react'
import '@testing-library/jest-dom/vitest'

afterEach(() => {
  cleanup()
})
```

Before this fix, the `test` block in `vite.config.ts` was silently ignored (the file imported from `'vite'` not `'vitest/config'`), so `@testing-library/react`'s DOM was not cleaned up between tests. This caused intermittent false failures where queries found accumulated elements from prior tests.

**Caveat**: This fix landed in a **feature commit** (`3776669` — the StepGuide implementation) rather than a dedicated `chore:`/`test:` commit. Worth noting if git-bisect needs clean separation later. See [08-process-retrospective.md](./08-process-retrospective.md) for discussion.

## Dependencies (`package.json`)

**Added**: `@codemirror/legacy-modes@^6.5.2`

The design spec originally specified `@codemirror/lang-lua`, which **does not exist** on npm. `@codemirror/legacy-modes` is the official CodeMirror 6 fallback package containing CM5-era modes, including Lua. It is used via `StreamLanguage.define(lua)`:

```ts
import { StreamLanguage } from '@codemirror/language'
import { lua } from '@codemirror/legacy-modes/mode/lua'

const luaSupport = StreamLanguage.define(lua)
```

`@codemirror/language` (for `StreamLanguage`) was already a transitive dep of `@uiw/react-codemirror` and did not need a direct install.

`@codemirror/theme-one-dark` is also already transitive — used for the editor theme.
