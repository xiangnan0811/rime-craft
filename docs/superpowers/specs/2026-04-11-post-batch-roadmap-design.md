# rime-craft 后续路线与契约对齐 — 设计文档

**日期**：2026-04-11  
**状态**：设计定稿，待书面复核  
**范围**：deep-content + unified Lua Extensions 批次之后的项目级路线、产品契约对齐、核心能力补齐、安全网建设与流程硬化

---

## 1. 背景与目标

### 1.1 当前状态

`rime-craft` 已经不是原型壳子，而是一个可运行的前端产品：

- 路由层已覆盖首页、编辑器、教程中心、主题工作室、方案对比、新手向导、配置画廊、方案详情
- 当前 `master` 的测试与构建为绿色
- `2026-04-11` 的 batch 已完成两类重要工作：
  - 21 篇教程的深度化重写
  - `special-input` 与 `lua-extensions` 的统一重构，形成新的三标签 `Lua 扩展` 模块

团队为这一批工作补充了完整的 review package，文档质量高、局部结论清晰，但它的观察视角主要集中在该 batch 自身，而不是整个产品的下一步路线。

### 1.2 当前真正的问题

项目下一步不能只跟着 batch 内部 follow-up 走。当前更高优先级的问题是：

1. **产品契约与实现边界不一致**
   - UI / 设计文档对平台支持的表述宽于当前真实导入导出能力
   - 设计文档承诺了项目级本地持久化，但当前实现主要是内存态
   - 设计文档承诺了基于 YAML CST 的高保真 round-trip，但当前实现仍以 typed model 映射 + 文本重建为主

2. **关键正式能力尚未补齐**
   - 项目自动本地保存
   - YAML 注释 / 格式保留的高保真编辑链路

3. **新 batch 的正确行为还没有足够的自动化守卫**
   - Lua 模块关键 UI 流程测试不足
   - 内容深度、交叉链接、module registry / capability 迁移更多依赖人工检查

4. **内容准确性与协作流程仍存在可信度风险**
   - 部分高风险教程中的 Rime 内部机制来自推断或社区经验
   - 大批量多代理执行暴露出 SHA 伪报、批次边界验证不足等流程问题

### 1.3 本设计的目标

这份设计文档不是直接执行单一功能，而是用于：

- 统一团队对“下一步真正应该做什么”的认知
- 锁定 4 个后续子项目的边界、顺序与完成定义
- 明确当前项目在产品承诺上的收口原则
- 为后续 `writing-plans` 拆分可执行实现计划提供母设计

### 1.4 非目标

本设计明确**不做**以下事情：

- 不直接展开到任务级、文件级、命令级实施步骤
- 不把 4 个相对独立的子项目压成一个单一实现计划
- 不在本阶段恢复 Linux / Android / iOS 为正式支持平台
- 不在本阶段将 repo 内流程硬化直接外溢到 home 级 superpowers / skills

## 2. 顶层决策

本设计锁定以下决策，后续实现计划必须遵守。

### 2.1 路线类型

采用**项目级总路线设计 + 分里程碑执行计划**模式，而不是一份覆盖全部后续工作的单一大计划。

原因：

- 当前工作天然分成 4 条相对独立的线
- 先统一边界与顺序，比过早写总执行清单更重要
- 每个里程碑后续都需要自己的实现计划与验收

### 2.2 总体策略

采用**契约先收口，能力分批补齐**的策略。

含义：

- 当“当前承诺”和“当前实现”不一致时，先让对外表述回到真实边界
- 对确认为正式能力的缺口，不降级为长期愿景，而是进入前两批里程碑

这意味着：

- 平台支持先收口
- 自动本地保存与高保真 YAML round-trip 继续保留为正式能力，但由后续里程碑补齐

### 2.3 平台支持契约

在下一轮对齐完成之前，`rime-craft` 的**唯一正式支持平台**定义为：

- `macOS`
- `Windows`

Linux / Android / iOS：

- 可以继续保留教程内容
- 不再保留“正式导入 / 导出 / 生成对应配置文件”的产品承诺
- 相关 UI 与文案不得继续暗示它们已经与 `macOS + Windows` 处于同等实现完成度

### 2.4 项目状态持久化契约

项目配置的**自动本地保存**被定义为正式近期能力，必须补齐，不降级为“用户手动导入导出即可”。

约束：

- 自动保存进入近期里程碑，不是长期 backlog
- 一旦补齐，应成为默认体验，而不是隐藏功能

### 2.5 YAML 能力契约

YAML 编辑能力的正式目标定义为：

- 保留注释
- 尽可能保留原格式
- 在现有编辑链路上支持高保真 round-trip

这项能力同样被定义为近期必须补齐的正式能力，不允许继续以“设计目标已达成”的口吻描述当前状态。

### 2.6 流程硬化范围

流程硬化先落在 **repo 内**，形成一套经验证的批次与代理协作规约；等仓库内运行稳定后，再考虑外溢到 home 级 superpowers / skills。

## 3. 方案比较与结论

### 3.1 方案 A：契约先收口，能力分批补齐

先统一正式支持矩阵和对外表述，再把自动保存与高保真 YAML 作为前两批能力补齐。

优点：

- 先止住认知误导
- 每个里程碑的责任更清晰
- 风险最小，利于团队在同一真相上推进

缺点：

- 会出现短暂的“先收紧承诺，再补能力”的过渡期

### 3.2 方案 B：能力追赶优先

尽量少动现有对外表述，优先实现自动保存和高保真 YAML，再统一文案。

优点：

- 表面变化更小

缺点：

- 在能力真正补齐前，仓库仍处于“说得比做得多”的状态

### 3.3 方案 C：双轨并行

一条线收紧契约，一条线并行补实现。

优点：

- 看起来最快

缺点：

- 协调成本高
- 最容易出现文档、设计、实现再次错位

### 3.4 结论

本设计采用 **方案 A**。

执行原则：

- **平台支持立即收口**
- **自动本地保存与高保真 YAML** 不降级，而是进入前两批必须交付的能力范围

## 4. 总体架构：4 个里程碑 / 4 个子项目

后续路线拆分为 4 个里程碑，每个里程碑对应一个独立子项目。

### 4.1 里程碑 M1：产品契约对齐

**目标**：统一“仓库说的”和“仓库做的”。

**范围**：

- 正式支持平台收口到 `macOS + Windows`
- 明确项目状态保存策略
- 明确 YAML 能力当前状态与近期目标
- 同步更新 UI、设计文档、说明文档中的相关表述

**不做**：

- 不在本阶段恢复其他平台的正式导入导出
- 不在本阶段重写 YAML 高保真引擎

**完成后应达到**：

- 用户在首页、向导、导入导出、设计文档、帮助文档中看到的能力边界一致
- 不再存在“全平台正式支持”或“高保真 YAML 已完成”的误导性表述

### 4.2 里程碑 M2：核心能力补齐

**目标**：补上仍被定义为正式能力的两项核心缺口。

**范围**：

- 项目配置自动本地保存
- 页面重开 / 刷新后的恢复策略
- 高保真 YAML round-trip 第一阶段实现
- 表单编辑 / YAML 编辑 / 导出之间的新同步规则

**依赖**：

- M1 已锁定契约和能力范围

**完成后应达到**：

- 用户重新打开页面可以恢复工作区
- 已导入配置文件在当前编辑链路下可保留注释与主要格式信息
- 现有导入、导出、分享主流程继续可用

### 4.3 里程碑 M3：安全网与批次补强

**目标**：把当前正确行为固化成测试和 CI 守卫。

**范围**：

- 内容深度检查
- 教程交叉链接检查
- schema capability / module registry 一致性检查
- Lua 模块关键交互测试
- orphan 行为与 Lua identifier 校验

**依赖**：

- M2 完成后才能锁定“新真相”

**完成后应达到**：

- 未来的内容改动、模块回归、迁移错误能被自动发现
- 新 batch 的主路径行为不再主要依赖人工 spot-check

### 4.4 里程碑 M4：内容准确性与流程硬化

**目标**：降低知识风险和协作风险。

**范围**：

- 复核 5 篇高风险教程中的 Rime 机制描述
- 在 repo 内落地批次执行 / 验收规约
- 引入 SHA 校验、严格构建边界、`DONE_WITH_CONCERNS` 处理规则

**依赖**：

- M1-M3 的产品与工程边界已稳定

**完成后应达到**：

- 高风险内容经过人工知识复核
- 下一轮团队或多代理协作已有明确护栏
- repo 内流程验证稳定后，可评估是否外溢到 home 级流程

### 4.5 顺序约束

里程碑顺序固定为：

`M1 -> M2 -> M3 -> M4`

原因：

- `M1` 必须先锁定真相，否则 `M2` 会边做边改需求
- `M3` 应锁定 `M2` 之后的稳定行为，而不是锁定当前过渡态
- `M4` 更偏知识和流程收尾，不应压过当前产品主路径问题

## 5. 关键技术决策

本节只锁定影响后续实现形态的关键决策，不写任务级实施细节。

### 5.1 自动本地保存与高保真 YAML 的实现方向

在技术层面有三种可能：

#### 方向 A：继续以 `RimeProject` 为唯一真源

做法：

- 给当前 Zustand store 接上 `persist(localStorage)`
- 继续使用 typed model -> YAML 重建链路

问题：

- 能快速补齐自动保存
- 但无法真正满足高保真 YAML round-trip 的目标

#### 方向 B：直接让 YAML 文档 / CST 成为唯一真源

做法：

- 长期持有每个配置文件的 `yaml.Document` / CST
- 表单层从文档投影，编辑时直接 patch 文档节点

问题：

- 理论纯度高
- 但对当前架构侵入太大，且不适合直接做浏览器持久化

#### 方向 C：混合架构

做法：

- 保留 `RimeProject` 作为表单 / 业务层投影模型
- 新增源文件工件层，维护 raw source 与运行时文档
- 新增可序列化工作区快照，用于自动保存

本设计采用 **方向 C**。

### 5.2 混合架构的核心原则

#### 原则 1：持久化存“工作区快照”，不存运行时文档对象

持久化层应保存：

- `project`
- 必要的 `editorUI`
- `sourceFiles`
- `version`

其中 `sourceFiles` 保存的是原始文本与元数据，不保存不可序列化的运行时对象。

#### 原则 2：运行时维护源文件工件层

每个源文件工件应包含：

- 原始文本 `raw`
- 文件类型 / 归属信息
- 运行时重建得到的文档对象
- 该文件与表单模型之间的字段绑定关系

#### 原则 3：同步规则必须双向明确

同步方向定义如下：

- **导入时**：原始文件进入工件层，再投影到 `RimeProject`
- **表单编辑时**：更新 `RimeProject`，再 patch 回源文件工件并刷新 raw
- **YAML 编辑时**：直接编辑 raw，parse 后反投影到 `RimeProject`
- **导出时**：优先导出当前源文件工件的文本；仅在源文件不存在时走生成路径

#### 原则 4：范围控制优先

高保真 YAML round-trip 第一阶段只覆盖当前核心链路：

- `default.custom.yaml`
- `squirrel.custom.yaml`
- `weasel.custom.yaml`
- 主 schema 的 `.custom.yaml`
- `custom_phrase.txt`

不把 Linux / Android / iOS 文件族纳入第一阶段目标。

### 5.3 为什么选择混合架构

选择该方案的原因：

- 兼容当前 UI 层已经围绕 `RimeProject` 形成的模块化结构
- 为“注释 / 格式保留”提供真实的技术抓手
- 能自然支撑自动本地保存
- 后续若扩展平台文件族，不需要重做整套状态模型

## 8. 风险与缓解

### 风险 1：团队继续按 batch follow-up 列表线性推进

**后果**：容易先做局部 polish，忽略产品契约错位。

**缓解**：将 `M1` 明确设为先决里程碑，后续计划必须先从契约对齐开始。

### 风险 2：自动保存与高保真 YAML 互相拖拽，导致 M2 失控

**后果**：M2 变成一个无限扩大的“重做编辑器内核”项目。

**缓解**：

- 采用混合架构，而不是完全切换唯一真源
- 第一阶段只覆盖核心文件族，不扩展到全部平台

### 风险 3：守卫锁定的是过渡态，而不是新真相

**后果**：M3 的测试和 CI 反而会给后续正确修正制造阻力。

**缓解**：M3 必须放在 M2 之后执行。

### 风险 4：流程硬化过早外溢到 home 级工作流

**后果**：把尚未验证的 repo 内规则扩散到更大范围，反而增加维护成本。

**缓解**：先 repo 内验证，再决定是否外溢。

---

## 9. 总体完成定义

当这份总设计完全执行完毕时，仓库应达到以下状态：

1. 用户看到的产品承诺与真实能力一致
2. `macOS + Windows` 成为明确、干净、可解释的正式支持矩阵
3. 自动本地保存与高保真 YAML 编辑成为正式能力，而不是设计愿景
4. Lua / 内容批次的关键行为拥有 CI 护栏
5. 高风险教程经过人工知识复核
6. 下一轮团队协作具备更可靠的 repo 内执行与验收规则

---

## 10. 后续拆计划原则

后续进入 `writing-plans` 时，必须遵守以下原则：

1. 不为这 4 个里程碑写一份单一的大实现计划
2. 每个里程碑单独拆实现计划
3. `M1` 与 `M2` 优先级高于 Lua 模块局部 polish
4. `M3` 的守卫应基于 `M2` 完成后的新行为
5. `M4` 先在 repo 内落地流程硬化，再决定是否外溢

这意味着下一步最合适的产物，不是一份“全项目实现清单”，而是：

- 一份总路线母设计（即本文）
- 多份按里程碑拆分的实现计划
